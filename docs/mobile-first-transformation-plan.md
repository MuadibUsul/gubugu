## 1. 改造目标

谷布谷下一阶段的目标不是重写产品，而是在现有完整业务基础上完成一次面向正式发布的收敛：

1. 以移动端体验为产品重心，同时为 PC 提供真正适合宽屏的响应式布局。
2. Web、PWA 和 Capacitor App 共用同一套 Next.js 后台、领域逻辑和 PostgreSQL 数据。
3. Android App 保持轻量，只承载 WebView、相机权限、系统返回、深链、分享和发布所需原生配置。
4. 优化扫描点亮、谷柜、换谷和社交展示，形成可稳定使用的核心闭环。
5. 修复当前隐私、数据边界、CI 和生产部署问题，再进入 Google Play 测试与上架流程。
6. 首发内容覆盖约十几个主流 IP、数百个热门 SKU；自动采集与人工维护并存。

北极星链路：

```text
发现 / 搜索 / 扫描
        ↓
      SKU 图鉴
        ↓
愿望 / 实物点亮 / 可换
        ↓
匹配 / 报价 / 履约 / 评价
        ↓
谷柜展示 / 收藏身份 / 同好关系
```

## 2. 已确认的产品决策

以下决策在本计划中视为已确认，不在实施阶段反复摇摆：

- 移动端是产品重心，但 PC 与手机使用各自适配的响应式布局。
- Web 和 App 共用一个模块化单体后台，不另建 App 专用业务后端。
- App 采用 Capacitor 薄壳，不开发独立原生业务界面。
- 公共图鉴和搜索结果始终展示原色商品图，不再用灰阶表达用户收藏状态。
- “点亮”代表实物与官方 SKU 建立可信对应，是公开拥有、稀缺展示和社交身份的基础。
- 高置信识别自动点亮；低置信识别展示候选并由用户确认；无法匹配则进入私密未鉴定收藏。
- 未鉴定收藏除不出现在他人可见主页外，日常查看和管理体验不做刻意降级。
- 完整换谷链路继续保留并优化，包括匹配、公开换谷帖、报价/反提、私信、履约和评价。
- 关注、Feed、角色收藏圈、排行榜、徽章和蹲谷通知继续维护，但不扩展为重社交平台。
- 用户图片、识别图片和目录资源均存储在自有 VPS；公开资产和私密资产必须物理或逻辑隔离。
- `.dc.html` 移动设计稿是移动端视觉与交互真源，品牌统一使用“谷布谷 / GUBUGU”。
- 内容录入采用“白名单爬虫 + DeepSeek 结构化处理 + 人工审核发布”，同时保留完整手动录入通道。

## 4. 目标技术架构

```text
响应式 Web / PWA             Capacitor Android 薄壳
        │                            │
        └──── HTTPS + Cookie/API ────┘
                         │
              Next.js 模块化单体
       RSC 页面 + Server Actions + /api/v1
                         │
       server/services + server/data + lib/domain
                         │
              Drizzle + PostgreSQL
                         │
        VPS 公共资产区 / VPS 私密资产区
```

架构约束：

- 保持单仓库、单后台和一套领域规则，不引入微服务、Redux 或 App 专属数据库。
- 页面读取进入 `server/data`；复杂写流程进入领域 service，再由 Server Action 或 Route Handler 调用。
- Web 继续优先使用 Server Components；只有相机、即时反馈、弹层和浏览器 API 使用 Client Components。
- Capacitor 默认加载生产 HTTPS 站点，原生层不复制收藏、识别或换谷规则。
- `/api/v1` 只在原生能力或未来客户端确实需要时补齐，不为“看起来完整”复制 Server Action。
- 公共目录图和用户私密扫描图使用不同存储命名空间、读取路由和缓存策略。

## 5. 响应式体验规范

### 5.1 布局层级

- 手机：单列 App 信息架构，底部五 Tab 为 `首页 / 谷库 / 扫描 / 换谷 / 我`。
- 平板：保持触控优先，可使用双栏、抽屉筛选和更宽的卡片网格。
- PC：恢复宽屏主容器、顶部导航、侧栏筛选和多栏详情，不显示移动底部 Tab。
- 扫描页在手机和 App 内为沉浸式全屏；PC 不提供伪相机入口，只给出移动端引导或二维码。
- 安全区、键盘顶起、横竖屏和系统返回必须在 Android 真机验证。

建议断点责任：

| 范围         | 主要模式                                 |
| ------------ | ---------------------------------------- |
| `< 768px`    | 移动 App 布局、底部 Tab、单列/双列商品墙 |
| `768–1023px` | 平板布局、双栏内容、折叠筛选             |
| `>= 1024px`  | PC 宽屏布局、顶部导航、侧栏与多列信息    |

断点只决定布局，不产生两套业务组件。页面应复用数据模型和语义组件，通过组合与 CSS 改变排布。

### 5.2 视觉规则

- 移动端以 `.dc.html` 设计稿为真源：纸张博物馆、象牙纸、墨色、朱红、古铜金、青黛。
- 亮色与暗色主题都需要通过，但商品图不得因主题或收藏状态被灰阶处理。
- 年轻用户正常字号，避免大标题、大图标和无意义的营销 Hero。
- 手机首屏直接出现搜索和内容；PC 利用宽度提高扫描效率，而不是把手机列居中放大。
- 点亮状态使用印章、边框、文案和动效表达，不改变公共商品图本身的色彩。
- 所有动效支持 `prefers-reduced-motion`，常规反馈保持在 120–220ms。

## 6. 核心领域规则

### 6.1 收藏与点亮

需要明确区分四类事实：

| 状态             | 含义                        | 是否可公开展示为拥有 | 是否可用于换谷库存 |
| ---------------- | --------------------------- | -------------------- | ------------------ |
| 无关系           | 未拥有该 SKU                | 否                   | 否                 |
| `wanted`         | 想要                        | 否                   | 否                 |
| 未鉴定扫描项     | 扫到实物但未匹配官方 SKU    | 否                   | 否                 |
| `owned + lit_at` | 实物已与官方 SKU 对应并点亮 | 是                   | 是                 |

- 现有“手动收进谷柜但未点亮”的 `owned` 状态需要在实施时收敛语义：保留为私密待确认记录，或迁移为独立收藏草稿；不得与公开拥有混淆。
- `exchange` 必须由已点亮拥有数量派生或受其约束，不能单独证明库存。
- 公共主页只显示已点亮 SKU；自己的谷柜同时显示已点亮、愿望、可换和未鉴定扫描项。
- 换谷收到的物品仍需重新扫描，才能成为接收方公开点亮藏品。

### 6.2 分级识别

识别结果分三档，阈值必须配置化并通过真实样本校准，不能只依赖当前硬编码的 `0.86`：

1. 高置信：服务端自动确认并点亮，返回明确的官方 SKU 和匹配证据。
2. 中/低置信但有可靠候选：展示有限候选，由用户确认后点亮。
3. 无可靠候选：保存为私密未鉴定收藏，不进入公开主页和换谷库存。

可信链路必须保持：

```text
相机拍摄
  → 服务端生成 embedding
  → 服务端记录 recognition_attempt
  → 自动确认或 candidateId 确认
  → 服务端解析 goodsId
  → 事务写入 owned + lit_at
```

- 浏览器永远不能直接提交 `goodsId` 获得点亮。
- 自动点亮和手动候选确认必须共用同一个服务端确认事务。
- Mock、缺少 embedding、过期请求、重放请求和非相机来源不得产生点亮。
- 上线阈值以“误点亮率优先低于漏识别率”为原则；错误自动点亮会直接破坏稀缺性信誉。

### 6.3 换谷与社交

- 保留当前无现金换谷模型和完整履约状态机。
- 优化顺序为：发现匹配 → 看懂互换关系 → 创建报价 → 最多三次反提 → 接受并锁库存 → 私信沟通 → 寄出/收货 → 双向评价。
- 正式条款只认不可变报价修订；私信不改变交易快照。
- 移动端先展示当前任务和下一步动作，历史记录与解释信息渐进展开。
- PC 使用双栏或主从布局，避免把 560px 手机卡片简单放大。
- 关注、Feed、收藏圈、排行榜、徽章与蹲谷继续维护，但入口必须服务收藏身份或换谷协作。

## 7. 数据与隐私改造

### 7.1 VPS 资产分区

```text
public catalog assets
  - 官方图、爬虫草稿审核后发布图、公开分享卡
  - 可使用长期公共缓存

private user assets
  - 未鉴定扫描图、待审核用户图、其他非公开原图
  - 不提供静态公开 URL
  - 通过鉴权 Route Handler 流式读取
  - 响应使用 private/no-store 或短时授权缓存
```

### 7.2 数据库要求

- 为 `user_scans` 增加所有权约束、合理的分数范围约束、RLS 与验证脚本覆盖。
- 用户 id 由自托管注册流程生成，凭据表 `local_auth_accounts` 与业务表分离；用户列保持裸 UUID，需要用户信息时 join `profiles`。
- 增加未鉴定项到候选/最终 SKU 的可追踪关系，便于未来重新匹配，但不强制增加复杂审核流。
- 识别确认、点亮和换谷库存写入必须使用事务、幂等键和并发复验。
- 账号删除必须级联或异步清理账号关联数据和 VPS 私密文件，并记录必要的法定保留例外。
- RLS 验证不能只覆盖旧表；每次新增用户数据表都必须进入真实数据库验证。

## 8. 内容与后台策略

首发目标：约 10–20 个主流 IP、数百个高热度 SKU，优先保证覆盖率和数据可信度，而不是追求全量。

内容管线：

```text
白名单官方来源
  → 限速抓取与断点续爬
  → 图片标准化与去重
  → DeepSeek 结构化中文化/字段补全
  → 草稿差异预览
  → 人工审核
  → 发布并生成 embedding
```

实施要求：

- 用可配置优先级维护 IP 白名单和热门 SKU 录入队列。
- 自动化只能生成草稿，不能无审核直接污染正式图鉴。
- 保留 IP、角色、系列、SKU、标签和官图的手动创建/编辑能力。
- 为重复 SKU、缺图、缺角色关系、无 embedding 和来源失效建立后台质量队列。
- 每个正式 SKU 保存来源、抓取时间和必要的版权/出处信息。
- 发布或换主图后自动触发 embedding 待处理状态；失败可重试且不阻断图鉴浏览。

      **缺的是采纳率**：仍有 44 处页面自己手写空状态文案。逐页收敛属于 Phase 3，计划本身也要求外壳稳定前不逐页精修。
- [x] 已在 dev server 上实测 390 / 768 / 1024 / 1280 / 1440：单列+底部 Tab → 平板触控优先 → 顶部导航且无底部 Tab，暗色主题一并验过。**Android WebView 未验**（需真机，见 Phase 7）。

完成闸门：无横向滚动；手机首屏紧凑；PC 不呈现窄屏放大版；键盘和底部 Tab 不遮挡操作。

### Phase 3：发现、图鉴与谷柜

目标：先打磨最高频的 `首页 → 谷库 → SKU → 谷柜` 路径。

- [x] 首页首屏保留搜索与真实内容，依次组织轮播、换谷市场、热门 IP、最近收录和排行。
- [x] 谷库在手机使用可折叠筛选，在 PC 使用侧栏/工具栏；所有商品始终原色。
- [x] SKU 卡用文字与状态装饰表达愿望、点亮和可换，不对商品图做灰阶。
- [x] SKU 详情优先展示图片、归属、规格和收藏动作；社区与换谷渐进展开。
- [x] “我/谷柜”使用紧凑资料头、点亮作品墙和清晰状态切换；未鉴定项只对本人出现。宽屏谷柜使用 5–6 列作品墙，不再锁在 720px 手机列。

完成闸门：匿名、本人、关注者和其他登录用户四类 viewer 的可见性均有测试和人工验收。

> 闸门现状：四类 viewer 的资料可见性矩阵已有单元测试；公开收藏查询只返回

> 四类身份和 360 / 390 / 768 / 1024 / 1280 / 1440 宽度做人工验收后，才把 Phase 3

### Phase 4：扫描点亮体验

目标：把产品差异化能力做到可相信、可恢复、可解释。

- [x] App/手机进入扫描页后直接申请相机并显示取景框，不增加无意义选择页。相机在 `RecognitionShell` 挂载时即启动，没有中间选择页，也不再提供上传入口。
- [x] 完成相机启动、拍摄、上传、识别中、高置信成功、候选确认、未匹配、失败重试和离线状态。`Phase` 现有 starting / live / scanning / candidates / matched / unmatched / offline / denied / error 九态。
- [x] 高置信自动点亮后提供短促稀缺感反馈，并清楚显示匹配到的官方 SKU：结果页给出「✦ 已点亮」徽标、SKU 名与匹配度，跳转带 `?lighting=success` 触发 SKU 页的印章动画。
- [x] 低置信只展示少量强候选，标示关键区分信息，不把相似度包装成真伪鉴定。服务端只回传前 3 个候选，卡片标注角色、系列、材质与尺寸，文案明写「相似度只是检索信号，不代表真伪鉴定」。
- [x] 未匹配项自然进入本人谷柜，并可继续查看、备注或稍后重新匹配。谷柜「未鉴定」区可展开写私人备注（`updateUserScanNoteAction`，服务端按 userId 过滤）并直达重新扫描。
- [x] 加入相机权限拒绝、永久拒绝、设备无相机、WebView 恢复和页面退出资源释放处理。区分 `NotFoundError` / `NotReadableError`；`visibilitychange` 切后台即停流、回前台重建；`online` / `offline` 事件驱动离线态。

完成闸门：真实 Android 设备完成连续扫描；错误/返回/旋转不残留摄像头；阈值样本达到预先记录的误点亮目标。

> 闸门现状：以上均为代码与桌面浏览器验证。**真机连续扫描、旋转与返回键残留、WebView
> 前后台切换都还没在 Android 上跑过**（需真机，与 Phase 7 一并验）。**阈值仍是默认
> 0.86 / 0.58，没有用真实样本校准**，所以「误点亮目标」这一条尚无数据支撑——
> 校准脚本见 `pnpm recognition:evaluate`，缺的是一批已知答案的实拍照片。

## 10. 跨阶段验证矩阵

每个改造阶段至少执行：

```bash
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

涉及数据库时追加：

```bash
pnpm db:migrate
pnpm db:seed
pnpm db:verify-rls
pnpm db:verify-trade
pnpm db:verify-lighting
```

涉及 Android 时追加：

```bash
pnpm cap:sync
cd android
./gradlew test
./gradlew bundleRelease
```

人工验证维度：

- 设备：Android 真机、Android WebView、Chrome Android、Safari iOS Web、Chrome/Edge PC。
- 宽度：360、390、768、1024、1280、1440。
- 身份：匿名、普通用户、关注者、内容所有者、审核员、管理员。
- 网络：正常、慢速、断网、请求超时、服务恢复。
- 数据：空数据、少量数据、数百 SKU、长名称、多角色、多图、无 embedding。

## 11. 明确不做

- 不创建第二套 App 业务后端或独立 App 数据库。
- 不重写为 React Native、Flutter 或完整原生 Android。
- 不引入支付、钱包、托管、仲裁或人民币 C2C 交易。
- 不训练自有视觉模型；先校准现有 embedding 检索和候选确认。
- 不把关注、Feed 或私信扩展为重内容社交平台。
- 不在首发阶段实现复杂多边物流、Push 平台或推荐系统。
- 不为了“架构完整”拆微服务、消息队列或新增全局状态库。

## 12. 里程碑顺序与阻塞关系

```text
M0 工程基线
  ↓
M1 隐私与点亮不变式
  ↓
M2 响应式外壳
  ↓
M3 图鉴/谷柜 + M4 扫描
  ↓
M5 换谷/社交 + M6 内容准备
  ↓
M7 Google Play 封闭测试
  ↓
M8 分批发布
```

不得跳过的阻塞关系：

- 私密资产和点亮事务未完成前，不进入真实用户扫描测试。
- 响应式外壳未稳定前，不逐页做视觉精修。
- 核心闭环和账号删除未完成前，不提交 Google Play 正式审核。
- 内容覆盖和 embedding 完整度未达标前，不宣传识别成功率。
- CI、数据库备份和回滚演练未通过前，不进行公开发布。

## 13. 首发完成定义

只有同时满足以下条件，才视为“可以上架”，而不是“代码基本完成”：

- 手机、平板和 PC 都使用适合其宽度的信息架构。
- Android App 保持薄壳，生产环境全程 HTTPS，无开发地址和明文流量。
- 图鉴始终原色，点亮状态清楚表达真实实物拥有和稀缺身份。
- 高置信自动点亮、低置信候选确认和未匹配私密收藏均稳定可恢复。
- 未鉴定照片无法被其他用户或无鉴权 URL 读取。
- 完整换谷闭环、私信和评价可在真机完成。
- 首发十几个主流 IP、数百个 SKU 达到内容质量标准。
- 自动采集和人工录入都能持续工作，正式发布必须经过审核。
- 所有工程、数据库、隐私、备份和 Android 发布闸门通过。
- Google Play 的 AAB、Data safety、隐私政策、账号删除、测试轨道和商店资料全部完成。
